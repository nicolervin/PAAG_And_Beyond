## Purpose

The Quality page maintains the approved project-wide repository of reusable Quality requirements, manual PFMEA control options, and reviewed PFMEA starting patterns, plus scenario-specific Process FMEA and Manufacturing Control Plan working-draft workflows. Contributors deliberately publish repository updates to linked Process at a Glance requirements and explicitly select applicable published assignments or manual options as Cause-level PFMEA Prevention and Detection controls. Classified PFMEA entries and their explicitly selected published Quality controls supply the MCP body-table projection.

## Connections

Repository definitions connect to scenario-specific Process at a Glance steps through `quality_requirement_assignments` and `work_elements.id`. PFMEA entries connect to the same stable Process step without changing upstream planning. Their Cause-level controls retain either the applicable published assignment identity or a project-wide manual-option identity, plus the acknowledged source version and collaborator-selected order. Nothing is auto-classified. Fishbone context remains inherited through the Process step rather than receiving a new direct relationship.

Process at a Glance and linked Yamazumi work use PFMEA only as a read-only criticality source: a Process step receives the derived **CTQ** tag when at least one linked PFMEA entry is classified `E`, `P`, `P-`, `Q`, or `E-`. The display does not write back to PFMEA, Process, or Yamazumi and creates no audit event.

## Scope

Quality requirement definitions, manual Prevention/Detection option catalogs, and PFMEA patterns are project-wide. Process-step assignments, PFMEA records, PFMEA control selections, and MCP working-draft items are scenario-specific, while a repository push can update assignments in more than one scenario within the selected project. A pattern acquires a critical-thread relationship only when its staged graph is assigned to a scenario-specific Process Function through hidden `work_elements.id`. The mixed-scope Quality page therefore displays the locked **Scenario-aware** boundary indicator; its PFMEA and Control Plan tabs always use the active scenario.

## Storage

`quality_requirements`, `quality_requirement_assignments`, and `quality_requirement_torque_details` retain their documented roles. PFMEA storage includes entries, Effects, Causes, RPN rows, Actions, two project-wide manual-option catalogs, two scenario-specific structured selection tables, and the normalized project-wide PFMEA pattern catalog. Patterns retain reusable Failure Mode, Effect, Cause, Recommended Action, suggested Classification, and ordered source suggestions; they never retain ratings, responsibility, completion evidence, or generated-row lineage. **Add PFMEA lines** lets collaborators select several live Process Functions, preview a blank or patterned graph for each, and stage fresh independent identities in the existing PFMEA draft. Quality-definition suggestions resolve only to an already-published assignment for the exact target step, while inactive or unavailable sources are disclosed and omitted. The advisory completion assistant highlights missing analysis without changing the rule that Process Function is the only required field. `pfmea_entries.class_code` stores the approved short code and `legacy_class_code` retains retired Critical Quality evidence. Structured control tags remain read-only in the flat grid; collaborators edit and copy them through the selected-Cause panel above the grid. Ordinary editable PFMEA cells retain native clipboard behavior. Duplication, RPN, source review, and explicit repository publication remain unchanged.

`control_plan_items` stores MCP-owned fields, nullable collaborator-curated **Pr. Nº**, exclusion, source acknowledgement/review state, and source identity/snapshots. The number is synchronized across every characteristic line for one hidden Process operation, displayed only on its first currently visible line, and used only to prefix characteristic numbers; it never replaces the Process relationship or characteristic ordering. The read-only **Station / Pitch** column separately repeats the current `work_elements.station` value, while the pinned read-only **Op ID** repeats the full live identifier—including within-Pitch stack position—on every characteristic line. Op ID remains derived through hidden `work_elements.id` and is not stored. When active numbers do not match live Op ID order, collaborators may stage **Renumber Pr. Nº by Op ID** to assign `1.0`, `2.0`, `3.0`, and so forth across all active operations; Undo discards the batch and Save & Refresh persists it atomically with one detailed audit event. Excluded and source-ineligible items are not renumbered. A mismatch with the PFMEA Pitch snapshot raises the existing source-review flag without persisting the live Pitch. New operations receive no-write suggestions until **Save & Refresh**, duplicate numbers across different operations require explicit save confirmation, and an editor-attributed one-time migration preserves the former Process-Seq-derived display. The active table is a live scenario-specific projection: one line per classified PFMEA/applicable published Quality-definition combination, deduplicated when the same assignment is selected in both PFMEA control lists, with one incomplete PFMEA-only fallback when no Quality control qualifies. Published Quality snapshots drive characteristic/specification display; Torque Type appends current Torque tool context. PFMEA controls and Actions appear as read-only evidence and never automatically populate Control method or Decision rule. Confirmed exclusion preserves content, Quality unlink preserves an orphan for explicit compatible relinking, PFMEA deletion removes dependent drafts, and scenario cloning remaps identities while retaining curated numbers. Issued status, document headers, approvals, and Word export remain unimplemented.

The peer **Process flow map** view is a read-only live projection and stores no map data. It shows every current Process step in the same full Op ID order used by PFMEA and Control Plan renumbering, even when no qualifying characteristic exists. Fishbone supplies structural lanes, Yamazumi feeder relationships supply exact branch joins, and active Control Plan projections supply blue Product, green Process, or amber unassigned characteristic nodes. Pr. Nº is shown only as document context. Filtering, keyboard navigation, details, pan, zoom, Fit, and full screen have no persistence or audit effect. Free-text decisions and Actions are detail evidence only; reject routing and document export remain deferred.

The Control Plan editor reuses `characteristic_placement` under the visible label **Characteristic type**; `Product / Part` is displayed as **Product** without changing stored values. Optional positive whole-number `characteristic_suffix` overrides are appended as label segments, so automatic numbering continues from `.9` to `.10`, and a Process number of `97.5` can produce `97.5.1`. Blank suffixes use the lowest available positive integer while reserving manual values, and suffixes never change `sequence` or source identity. Lines are grouped by hidden `work_elements.id`; repeated Process number and Operation cells, plus identical repeated Machine / fixture values, are blanked only in rendered/exported copies because Streamlit does not provide merged cells. Not assigned characteristic types remain visible and flagged.

## Applicable standards

Follow the complete Shared Editable-Table Implementation Checklist in `DESIGN_SYSTEM.md`, including filtering, direct entry where the row grain permits it, stable hidden IDs, native row selection, relationship-safe confirmed deletion/exclusion, filtered Excel export, **Undo**, and the footer **Save & Refresh** action. Every persisted save, bulk edit, deletion, exclusion, restore, relink, source review, and push must use `record_audit_event()` with Editor attribution, affected rows, and the store timestamp when supplied. Keep one **History** expander at the bottom of the page with Requirements, PFMEA, and Control Plan history tabs. Use canonical terminology and the traditional AIAG PFMEA/MCP field labels documented in `PFMEA_CONTROL_PLAN.md`.
