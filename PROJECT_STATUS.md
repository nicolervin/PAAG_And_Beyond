# Project status

_Reviewed September 11, 2026_

## What this project is

Process at a Glance is a local planning app for cross-functional collaborators preparing a new assembly process. It is intended to keep the product definition, parts, assembly order, work steps, timing, workstation balance, requirements, and open questions together instead of spreading them across separate spreadsheets.

The app is still a prototype. It runs on one computer, stores its records and uploaded images locally, and starts with sample data when no data file exists.

## Main screens and features

- **Overview** — Creates projects, shows headline counts, and edits the project definition. Its standard Planning scenarios table lists current and previous branches (including archived scenarios), supports filtering, direct entry and multi-row paste, external saved-row sorting, filtered Excel export, row Details, and audit history. Saving a new row clones the currently viewed scenario's scenario-owned planning data and makes the new branch the shared scenario view across pages.
- **Questions and concerns** — Keeps questions, concerns, decisions, and assumptions with owners, priority, status, and links to parts or stations.
- **Import PITS and export** — Imports ordinary Excel/CSV bills of material, the preferred ID-based PITS workbook, or older Level 1–11 PITS sheets. The ID-based route keeps source revisions and flags changed records for review. It also exports a multi-sheet Excel planning snapshot, including a flat sheet for Lucid data linking.
- **Model definitions** — Maintains official model numbers, team-friendly names, annual volumes, and active/inactive planning choices. It also defines product features and maps each model to its feature choices.
- **Parts Catalog** — Maintains the part catalog, feature-based model applicability, revision, notes, and source. Newly created manufacturing assemblies also receive a linked Parts Catalog row so the completed subassembly can be placed and handled again through the normal Fishbone and downstream-planning workflows; its model applicability is derived from Assembly grid mappings. Its scenario-specific Active checkbox hides inactive parts from downstream Fishbone, Process at a Glance, Pin Map-linked work, and scenario-export views while preserving their catalog records and saved links. Parts can have a main CAD image plus extra views; image controls live in Part Details and pasted Windows screenshots save immediately as the Primary CAD image. For linked completed-subassembly parts, the right side of Part Details also shows the assembly's current mini-BOM as a read-only table beside the photos, using the same component records edited through Assembly grid Details. The main table supports filtering, direct row entry and multi-row paste, external sorting, selected-row actions, deletion confirmation, Excel export, and a limited history view.
- **Assembly grid** — Provides a project-wide workspace with a protected Top-level packaged unit row immediately below the feature headers, followed by one or more Fishbone-section groups of real EBOM categories by active official model. Each model cell accepts one complete assembly number through its **Part number** field, alongside direct model mappings, continuously synchronized section values, active feature headers with saved visibility, nested mini-BOM quantity editing, completed-subassembly nesting, confirmed custom-grid deletion entry points, and Details access to images, the mini-BOM, retained Task 04 catalog metadata, and the full assembly deletion workflow. Assembly Details appears above the full catalog and deletion workspace; Images are its first/default tab, Mini-BOM is second, and the former Feature rules tab is hidden.
- **Parts to fishbone** — Builds the product's assembly framework, including main sections and nested subassemblies. Its deterministic depth-first framework traversal is shared through `assembly_section_walk_order()`, preserving main-spine `(sequence, name)` order, recursively inserted children, hierarchy depth, and the established orphan fallback. Collaborators can place approved catalog parts into that framework, record positive decimal quantities and uses, order them, and view the result as an interactive fishbone with images and feature filtering. A lightweight section-level list opens related assembly numbers on the shared Assembly grid page. Section deletion uses one combined continuity target for affected Yamazumi areas, Process at a Glance part requirements, assembly Built/Installed references, and assembly-grid category Built/Installed references; validates Yamazumi uniqueness and category-name collisions; removes source-section feature-visibility preferences; relocates mini-BOM uses for Built-section changes; and returns every other removed placement to Not placed.
- **Yamazumi** — Creates/imports pitch addresses and work elements, defines work regions, compares model variants, and lets collaborators draft within-pitch reordering or cross-pitch/Unassigned moves before one atomic **Save & Refresh**. Empty areas open a one-per-visit guided pitch-range dialog using an audited project-wide line-code default and editable Fishbone-derived section-code suggestion. Each scenario saves a Yamazumi-only Seconds, Minutes, or Hours preference while canonical storage remains in seconds. Pitch addresses are scenario-wide case-insensitively unique, and the board uses numeric-aware Op ID order with feeder-chain adjacency. A dedicated **Copy to another area** workflow atomically copies saved pitches and/or work elements within the project. Subassembly and Kitter feed relationships remain validated and cycle-protected. Yamazumi no longer stores or edits flags; linked work displays live read-only CTQ and Safety tags derived from PFMEA Classification and active Safety requirements.
- **Process at a Glance** — Brings selected Yamazumi work into an ordered plan and pairs fishbone parts with the work that consumes or subsequently handles them. Its compact table displays a live, read-only Op ID derived from Fishbone mainline/subassembly hierarchy, the stable Yamazumi relationship, pitch address, and centerline-outward stack position; incomplete links display explicit guidance instead of a guessed identifier. **Phase 3 — inline pitch-level visual summary is complete and verified:** each row's Details action opens the selected pitch beneath the table, automatically selects the clicked Work Element's five-card page, supports Back/Next navigation, and renders a responsive 16:9 snapshot with paired Parts Catalog images or placeholders, Yamazumi time, Models, qualifying Ergonomics and Torque tags, and a generated-date/scenario footer. Consume-only work is green, Handle-only work is orange, and missing, null, mixed, or part-less classification remains neutral gray because no approved persisted Waste classification exists. New part pairings default to Consume, can be switched to Handle, and identify the exact **Use / installation location**. A sole location is selected automatically; multiple locations require an explicit choice, and each option shows its scenario-specific remaining Consume allowance or Handle eligibility before the store layer enforces the hard placement rules. Pairing work without a part remains unchanged. The pairing workspace retains its catalog-part search and can find similar parts across every Fishbone section, choose a target section when placing a part, move or add an existing use, or create a minimally complete catalog part and Fishbone placement without leaving the page. It also includes filtering, pitch-only bulk edits, bulk deletion, imperial-unit Excel export, and history. The legacy Process status value remains stored for compatibility but is no longer displayed, filtered, or edited in the by-pitch table. The former editable tabbed per-step Details dialog and the Total work content / Target takt / Pitches represented summary with its Draft Yamazumi bar chart remain retired; their persisted Process data remains intact.
- **Pin Map** — Presents the active scenario as a read-only line map, placing explicitly linked Process at a Glance work above each Yamazumi workstation or pitch. It supports area, pitch-status, pitch-type, and keyword filters plus a filtered Excel export.
- **Quality** — Uses a Scenario-aware page with **Requirements repository**, **PFMEA**, and **Control Plan** tabs. The repository remains project-wide with direct entry, relationship-safe deletion, explicit publication, assignment management, and a cross-scenario linked-requirements view. PFMEA is scenario-specific, retains its normalized graph and structured controls, and stores the approved short Classification codes with read-only legacy evidence. The Control Plan tab is a scenario-specific MCP working draft derived from classified PFMEA entries and explicitly selected published Quality controls. Collaborators curate a nullable one-decimal **Pr. Nº** per Process operation; it is synchronized across that operation's characteristic lines, drives only their visible prefixes, and is retained through lifecycle and scenario-cloning workflows. Optional positive whole-number Characteristic suffix overrides affect labels only, while automatic suffixes reserve manual values and continue from `.9` to `.10`. New operations receive no-write suggestions, duplicate Process numbers and duplicate manual suffixes require explicit save confirmation, and the existing Process relationship remains unchanged. The reused placement field appears as **Characteristic type** with Product, Process, and Not assigned choices. Lines are grouped by Process operation, with repeated operation-level values blanked only in rendered/exported copies because the grid cannot merge cells. The table also displays published specification and Torque context and persists collaborator-authored Machine / fixture, placement, sample, Who, Control method, Decision rule, exclusion, and source-review state. Confirmed exclusion preserves content; source-ineligible and orphaned items remain reviewable and explicitly relinkable; scenario cloning remaps PFMEA and Quality links. One bottom History expander groups Requirements, PFMEA, and Control Plan. Issued status, document headers, revision/approval workflow, Word export, and the roadmap's deferred Phase 10 Process Flow Map remain unimplemented.

## Recently implemented

### Task 09 — Grid-based assembly-to-model mapping

The project owner confirmed the schema and interaction design on September 2, 2026. Implementation completed on `Nicole_assembly_grid_editor` on September 3, 2026, with completed-subassembly Parts Catalog integration added on September 4, 2026. The existing Task 04 assembly infrastructure remains intact, while `app_pages/assemblies.py` is now the project-wide, section-selected grid and primary entry point. Each persisted EBOM category has official and plain-English names, row order, and one authoritative Installed section. Each active-model cell maps that category directly to one real `manufacturing_assemblies` record, and those mappings are the authoritative model-applicability source. Components remain that mapped assembly's existing `manufacturing_assembly_components` rows. Legacy `manufacturing_assembly_feature_rules` rows remain stored for compatibility but are hidden and no longer evaluated.

The implemented project-wide tables are `assembly_grid_categories`, `assembly_grid_model_mappings`, and `assembly_grid_feature_visibility`. Active features appear by default; inactive features never render. Model filtering is browser-session state only. Each cell accepts the complete final assembly number in one **Part number** field; the former root, suffix, and full-override controls are retired. Editing a saved cell's Part number to an unused number renames the same assembly in place, retaining its stable ID, mapping, mini-BOM, images, and other dependent data instead of creating a replacement record. Editing it to another same-category assembly's existing number opens a non-dismissible relationship-aware merge confirmation; confirmation redirects the old mappings, displays the target assembly's authoritative mini-BOM after refresh, deletes the superseded assembly and its disclosed dependents, and records both grid and catalog audit history in one validated workflow. Stable focus restoration keeps single-click cell entry and forward/reverse Tab navigation on the intended visible grid control when committing a prior draft value causes a rerun. **Add Subassembly** creates grid rows, while each mapped assembly's **Add part** control lists the Part number and Part Name for every eligible exact Fishbone use. Both identifiers remain visible in saved and draft mini-BOM rows. Existing Fishbone uses can be added repeatedly in the in-memory grid draft, then persisted together by one **Save & Refresh**. Only final assembly relationships and explicitly saved mini-BOM changes are persisted. The Components v2 grid uses its documented screen-specific selection/deletion exception, while Python retains the non-dismissible confirmation, relationship disclosure, validation, atomic write, audit, reset, toast, and rerun requirements.

Every new assembly now atomically creates or reuses a linked Parts Catalog row through `manufacturing_assemblies.catalog_part_id`. Generated rows use the assembly number, assembly/category name, quantity 1, revision 0, and source `Assembly grid`, and inherit the existing default-active-in-each-scenario behavior. Linked assembly parts derive their model applicability from direct grid mappings instead of Parts feature rules. Assembly renames synchronize an unused number to the linked part; confirmed merges preserve the destination catalog part and its downstream relationships. Assembly deletion preserves the part, while direct deletion of a still-linked part is blocked with the owning assembly disclosed. The repeatable upgrade backfilled all 5 current assemblies, passed SQLite integrity and foreign-key validation, and recorded one `Parts` / `Assembly catalog backfill` audit event for the five links.

Category Installed section uses continuous synchronization. Changing it through **Save & Refresh** atomically updates every distinct currently mapped assembly, while a conflicting existing assembly is blocked from being mapped silently. A mapped assembly's Installed section is managed by its category; after the final mapping is removed, the assembly retains its last value and becomes independently editable. One real assembly may serve multiple models only inside one category. Project-wide validation blocks any final state that maps one `manufacturing_assemblies.id` to more than one distinct category, while allowing a complete atomic move between categories.

The Assembly grid now defaults to **All active sections** and can show any selected set of Fishbone sections as labeled groups with shared model and active-feature filters. One Save & Refresh validates and writes every displayed group atomically while preserving unselected sections and hidden models. A completed assembly from any displayed section appears as a distinct **Subassembly** mini-BOM option. Saving reuses or creates its completed-part Fishbone use in the parent assembly's Built section, then stores the ordinary quantity-bearing mini-BOM relationship. The operational nesting graph is many-to-many and comes from mini-BOM containment; validation blocks self-links, indirect cycles, and child assemblies that do not cover every official model mapped to the parent. Automatically created Fishbone uses and parent/child relationships are included in Assembly mini-BOM and Fishbone audit details.

One protected **Top-level packaged unit** category now renders directly below the active feature headers and above every Fishbone-section group, even when its final Built section is outside the current section filter. It has one final assembly mapping per active official model, a required selectable final Built section, and an optional Installed section. The structural row cannot be deleted, although its mappings and components use the standard confirmed clear/delete workflows. It may nest completed subassemblies from every active Fishbone section; ordinary parts remain constrained to exact uses in its selected final Built section. Changing the row's Built section atomically synchronizes its mapped assemblies and moves their referenced mini-BOM Fishbone uses to that section.

The local database was backed up and passed SQLite validation before the approved reset removed 2 prototype assembly records, 1 dependent component, and 1 dependent feature rule. Parts, Fishbone sections and uses, models, features, and non-assembly uploads were preserved. The backup remains local beneath ignored `data/backups/`, and the reset is recorded as `Assemblies catalog` / `Prototype data reset` under Nicole Ervin.

### Task 03 continuity extension required by Task 09

The Fishbone section-deletion workflow now detects all six continuity reference types: Yamazumi areas, Process at a Glance part requirements, assembly Built sections, assembly Installed sections, category Built sections, and category Installed sections under the same one-target picker.

`assembly_section_delete_impact()`, target validation, `delete_assembly_sections()`, and the combined disclosure dialog now include the Task 09 references. The target validator retains cross-scenario Yamazumi protection and rejects category collisions on trimmed, case-insensitive official EBOM category name or Display name. Every rejection identifies the target section, incoming category, exact colliding field and value, and conflicting target or incoming category, then instructs the contributor to choose a different target. No inline rename flow is present.

The six reference types are re-pointed in one transaction. Source-section feature-visibility preferences are disclosed and removed rather than merged into the target. Fishbone saved-state Undo captures and restores Task 09 categories, mappings, and preferences with stable identifiers, avoiding `ON DELETE RESTRICT` failures or lost grid data.

## Unfinished or broken

### Incomplete workflows

- Ergonomics Phase 1 provides schema and data access for project-wide part weight and hazard options, scenario-specific Handle/Consume part-use classification, Ergonomics reviews, and normalized hazard selections. Phase 2A classifies newly created Process part pairings and links each one to an exact Fishbone placement, while deliberately leaving the 16 pre-existing compatibility-`NULL` rows unchanged and omitting a general editor for saved pairings. Phase 2B now provides the scenario-specific Ergonomics review editor, visible Linked/Unlinked state and filtering, direct legacy/pre-PAAG entry, automatic `Started` reviews for newly created Process steps, relationship-aware linking and merging, confirmed deletion, Current editor audit history, and content-preserving Work Element deletion through `ON DELETE SET NULL`. The September 9 risk amendment is implemented: every review has an independent controlled `risk_classification`, legacy reviews are factually initialized to `Not yet assessed`, and Process at a Glance derives a read-only red tag when any same-scenario linked review is Open/Pending and Red/Favorable Red. No acknowledge/dismiss field or control exists. The September 9 trigger-coverage audit found four creation paths: Process direct entry (single and bulk) and Yamazumi reconciliation were already covered, while scenario cloning and new-database sample creation were not. All four now use one atomic store-layer creator for the Process step and baseline review. The idempotent historical migration was applied to the local database after a verified backup and created 12 missing baseline reviews; no Process steps remain without a linked review. The September 9 scenario-cloning amendment is also implemented: cloning copies every source review and hazard selection with new IDs, preserves Unlinked reviews, remaps cloned Work Element and Process part-use relationships, nulls a part-use relationship when no cloned counterpart exists, and removes only the automatically generated baseline placeholder when copied reviews target that step. Multiple source reviews linked to one step are all retained. The Ergonomics page displays the active scenario's current takt time to support manual reassessment of frequency-driven risk; cloning stores no takt comparison and creates no re-review flag. The inline 16:9 Standard Work detail, automatic weight-based review triggers, linked-source change detection and re-review flags, and the derived production-readiness calculation remain deferred.
- The export to Lucid is a one-way snapshot only. There is no controlled ongoing synchronization or settled Lucid identifier strategy yet.
- Change history is partial rather than complete. Parts, process-planning, and several Yamazumi actions record standardized history, but not every editable screen and not every individual engineering change does so.
- Some older editable sections still do not provide the same bulk tools or audit coverage, even though their save-action placement now follows the shared table-footer pattern.
- `app_pages/assembly_sequence.py` is an older assembly-fishbone page that is no longer linked in the app navigation. It appears to be leftover code alongside the newer Parts to fishbone screen.

### Verification gaps

- The automated suite remains small and does not exercise most editing, confirmation, save, deletion, or audit workflows. Compilation and page smoke checks therefore remain necessary, and browser-only behavior can still regress without being caught automatically.
- Import parsing was inspected but not tested with a set of saved example workbooks in the repository. Ordinary BOM, current PITS, and legacy PITS variations therefore depend heavily on real-file testing.
- Image upload, clipboard paste, the interactive fishbone, and Yamazumi drag-and-drop need browser-level tests; the available smoke check cannot fully exercise them.

## Overall assessment

The project has grown beyond a simple mock-up: the core product structure, model/part planning, fishbone, Process at a Glance workflow, scenario-specific Pin Map, project-wide Quality requirements repository, scenario-specific Process links, PFMEA, and MCP working-draft body, local persistence, revision-aware PITS import, scenario branching, and Excel export are substantially present. Issued Control Plan document generation remains deferred. The highest-value remaining work is to bring the remaining editable screens up to the shared table standard and add repeatable tests around imports and the major save and deletion paths.
